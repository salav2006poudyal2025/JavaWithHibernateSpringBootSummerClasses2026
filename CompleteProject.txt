MY SPRING WEB — COMPLETE PROJECT DOCUMENTATION
================================================

Document purpose
----------------
This report documents the implementation present in the MySpringWeb source tree. It is written as a technical handover and project-submission report: each feature, component, data flow, and configuration item below is tied to an actual project file.

1. PROJECT OVERVIEW
-------------------

Project name: MySpringWeb (Maven artifact: MySpringWebGrp1)

Objective: Deliver a Java 17 Spring Boot web application in which visitors can register, authenticate through a browser session or JWT API login, manage users, upload and view images, and use email and cloud-storage integrations.

Problem solved: The application combines user account management with protected web and API workflows. It provides a browser-facing interface for registration, login, user administration, and image galleries, while also exposing authenticated REST user-management APIs for programmatic clients.

Technology stack:
* Java 17; Spring Boot 4.1.0; Maven.
* Spring MVC, Thymeleaf, Spring Security, Spring Data JPA, Bean Validation, Spring Mail.
* Hibernate/JPA with a MySQL-compatible production datasource; H2 is configured for tests.
* JJWT 0.11.5 with HS256 signing for JSON Web Tokens.
* Cloudinary HTTP5 SDK for cloud image storage.
* Lombok for entity boilerplate generation.
* Docker with Eclipse Temurin 17; Render blueprint configuration.

Architecture used: layered N-tier Spring MVC architecture. The packages Model, Repository, Service, Controller/RController, Configuration, and Exception separate persistent data, data access, business rules, delivery channels, framework setup, and error translation.

Deployment platform: Render is configured through render.yaml to deploy the Docker-based web service. Docker exposes application port 8080. Runtime credentials are supplied as environment variables.

Database: the production configuration receives DB_URL, DB_USERNAME, and DB_PASSWORD from the environment and uses the MySQL JDBC driver. Hibernate schema management is configured with spring.jpa.hibernate.ddl-auto=update. The test profile uses in-memory H2.

2. PROJECT ARCHITECTURE
-----------------------

The implementation follows the following N-tier request path:

Browser / API client
        |
        v
Presentation layer: Thymeleaf templates and REST JSON payloads
        |
        v
Controller layer: MVC controllers and REST controllers
        |
        v
Service layer: user business operations, BCrypt authentication, registration email trigger
        |
        v
Repository layer: Spring Data JPA repositories
        |
        v
Database / external services: MySQL/H2, SMTP, Cloudinary

Presentation layer
Files: src/main/resources/templates/*.html and src/main/resources/static/css/styles.css.
Purpose: renders HTML pages, binds forms, renders lists supplied through Model/session attributes, and displays returned image data. Thymeleaf expressions such as th:action, th:href, th:each, th:text, th:value, and th:src connect templates to controller-supplied data.

Controller layer
Files: Controller/MappingClass.java, SignupController.java, UserController.java, GalleryController.java, MailController.java; RController/RControllerClass.java and AuthRestController.java.
Purpose: maps HTTP routes, reads form values/request bodies, constructs models or redirect messages, invokes services/repositories, and selects an HTML view or HTTP response.

Service layer
Files: Service/UserService.java, UserServiceImpl.java, EmailService.java.
Purpose: abstracts user operations behind an interface; hashes passwords, validates login credentials using BCrypt, delegates persistence, and sends the registration email after a saved user has an email address.

Repository layer
Files: Repository/UserRepository.java, ImageRepository.java, Image2Repository.java.
Purpose: extends JpaRepository to provide create, read, update, delete, and findAll operations. UserRepository additionally derives findByUsername from its method name.

Database layer
Files: Model/UserTable.java, ImageTable.java, ImageTable2.java; application.properties.
Purpose: maps Java entity objects to relational records. UserTable is associated with locally stored image records and Cloudinary-image records. Database schema changes are maintained by Hibernate update mode.

Data-flow example: a signup POST reaches SignupController, which creates a UserTable and calls UserService.saveUser. UserServiceImpl BCrypt-encodes its password, calls UserRepository.save, then calls EmailService. JPA/Hibernate persists the entity to the datasource; the controller redirects the browser to login with a flash confirmation message.

5. DATABASE, HIBERNATE, AND JPA
-------------------------------

Entity design
* UserTable.java is the user entity. It has identity-generated int id, username, email, password, a list of ImageTable images, and a list of ImageTable2 cloudImages.
* ImageTable.java is the local-gallery entity. It has an identity-generated id, a LOB/MEDIUMBLOB-compatible String image holding Base64 image data, and a user association.
* ImageTable2.java is the Cloudinary-gallery entity. It has an identity-generated id, a String imageUrl containing the returned secure URL, and a user association field.

Table structure and relationships
@Entity establishes persistence mappings. UserTable owns two @OneToMany collections mapped by the user property; ImageTable and ImageTable2 each use @ManyToOne with @JoinColumn(name = "user_id"). This produces a one-user-to-many-images relationship for both image storage approaches. CascadeType.ALL on UserTable's collections cascades entity operations to associated images.

Validation
File: Model/UserTable.java.
username and password use @NotBlank; email uses @NotBlank and @Email. The global exception advice converts ConstraintViolationException into a 400 response when such violations are raised in a request flow.

CRUD implementation
* UserRepository inherits save, findById, findAll, and deleteById.
* UserServiceImpl exposes saveUser, findById, findByUsername, findAllUsers, deleteUser, and authenticate.
* RControllerClass implements GET, POST, PUT, and DELETE user APIs.
* UserController implements browser edit, update, and delete actions.
* ImageRepository and Image2Repository save local and Cloudinary image metadata respectively.

Transactions and persistence flow
Spring Data JPA repository save and delete operations are executed through Spring Data's repository transaction support. A user save flows from controller to UserServiceImpl, to UserRepository, then through Hibernate to the configured datasource. An image save similarly flows through the relevant image repository. Hibernate's update schema setting maintains the mapped schema at application startup.

6. THYMELEAF FRONTEND
----------------------

signup.html
Route: GET /signup; form POST /signup. It collects username, email, and password and uses th:action for the route. It displays controller flash messages through ${message}.

login.html
Route: GET/POST /login. The form posts credentials with th:action="@{/login}". It displays login failure feedback (${message}) and signup completion feedback (${signupSuccess}); it links to the signup page.

home.html
Route: GET /home. It inserts navbar.html and uses th:each over ${totalUsers} to render user identifiers and names. It posts user ids to editUser and deleteUser actions.

galleryPage.html
Route: GET/POST /gallery. The multipart form posts an image file. It iterates session.totalImages and creates data:image/jpeg;base64 sources from the stored Base64 content.

galleryPage2.html
Route: GET/POST /gallery2. The multipart form uploads to the Cloudinary workflow. th:each iterates ${cloudImages} and th:src displays each stored HTTPS URL.

Supporting views
firstPage.html is the landing page, nextPage.html is an auxiliary route, navbar.html supplies shared navigation, editPage.html binds a selected UserTable's fields for update, and mailPage.html is available from the authenticated-session mail route. static/css/styles.css provides the shared registration/login styling.

Navigation flow: landing page -> signup or login -> home -> user management, local gallery, Cloudinary gallery, or mail view -> logout. The navbar displays the username held in the HTTP session.

7. SPRING SECURITY AND SESSION HANDLING
----------------------------------------

File: Configuration/SecurityConfig.java.
SecurityConfig enables web security and registers a SecurityFilterChain. It permits public access to /, /login, /signup, static CSS/JS/images, and /api/auth/**. All other /api/** endpoints require an authenticated Spring Security context. Other HTML routes are delivered with their controller-level session checks where used.

CSRF configuration: csrf.disable() is explicitly configured. This permits the existing form and stateless API interaction model without a generated CSRF token requirement.

JWT filter placement: the configured JwtAuthenticationFilter is inserted before UsernamePasswordAuthenticationFilter. A valid Bearer token therefore establishes authentication before the authorization rules evaluate protected API paths.

Browser-session handling
Files: Controller/MappingClass.java, GalleryController.java, MailController.java, templates/navbar.html.
Successful form login creates an HttpSession and stores username. Gallery and mail routes inspect the session username before rendering their protected views. Logout obtains the existing session without creating a new one and invalidates it. The navbar reads session.username for its greeting.

8. BCRYPT PASSWORD SECURITY
---------------------------

Files: Configuration/SecurityConfig.java and Service/UserServiceImpl.java.

SecurityConfig exposes PasswordEncoder as a BCryptPasswordEncoder bean. When a user is saved, UserServiceImpl checks whether the password is already BCrypt-formatted and, when it is raw, calls passwordEncoder.encode before persistence. During browser and REST login, authenticate retrieves the user by username and calls passwordEncoder.matches(rawPassword, storedHash).

This means the database receives a BCrypt hash rather than the raw registration password. BCrypt uses a per-hash salt and computational work factor, so the stored hash is appropriate for password verification without recovering or storing the original password.

9. JWT AUTHENTICATION
---------------------

Files: Configuration/JWUtil.java, JwtAuthenticationFilter.java, SecurityConfig.java; RController/AuthRestController.java.

Token generation: POST /api/auth/login accepts username and password request parameters. AuthRestController delegates credential checking to UserService.authenticate. On success it calls JWUtil.generateToken and returns JSON containing token.

JWUtil: the component reads jwt.secret and jwt.expiration, creates an HMAC signing key from the secret, and creates a compact HS256 token with subject=username, issued-at time, and expiration time. It parses claims to extract the subject and expiration, then validates subject equality and expiry.

Protected API access: JwtAuthenticationFilter extends OncePerRequestFilter, so it executes once per request. It reads Authorization, accepts the Bearer prefix, parses the token subject, validates the token, creates UsernamePasswordAuthenticationToken, attaches request details, and stores it in SecurityContextHolder. SecurityConfig then allows the authenticated request through the /api/** authorization rule.

JWT authentication flow

Client -> POST /api/auth/login (username, password)
       -> AuthRestController
       -> UserServiceImpl.authenticate
       -> UserRepository.findByUsername + BCrypt matches
       -> JWUtil.generateToken (HS256, subject, issue time, expiry)
       -> 200 OK {"token":"<JWT>"}

Client -> GET/POST/PUT/DELETE /api/**
       -> Authorization: Bearer <JWT>
       -> JwtAuthenticationFilter extracts token
       -> JWUtil parses and validates subject/expiry/signature
       -> SecurityContextHolder receives authenticated principal
       -> SecurityFilterChain authorizes /api/**
       -> REST controller executes and returns ResponseEntity

10. EMAIL INTEGRATION
---------------------

Files: Service/EmailService.java, Service/UserServiceImpl.java, src/main/resources/application.properties, render.yaml.

Spring Boot's mail starter provides JavaMailSender. The production properties set SMTP host smtp.gmail.com, port 587, authentication, and STARTTLS. MAIL_USERNAME and MAIL_PASSWORD are environment-backed values.

Registration-email workflow:

SignupController -> UserServiceImpl.saveUser -> UserRepository.save
                 -> EmailService.sendRegistrationEmail
                 -> SimpleMailMessage (from, recipient, subject, plain-text body)
                 -> JavaMailSender -> configured SMTP server -> recipient inbox

The message is personalized with the registered username and uses the subject "Welcome to MySpringWeb". EmailService contains delivery exception handling local to the send operation.

11. CLOUDINARY AND IMAGE UPLOAD INTEGRATION
--------------------------------------------

Files: Configuration/CloudinaryConfig.java, Controller/GalleryController.java, Model/ImageTable2.java, Repository/Image2Repository.java, templates/galleryPage2.html.

CloudinaryConfig reads CLOUDINARY_CLOUD_NAME, CLOUDINARY_API_KEY, and CLOUDINARY_API_SECRET through application properties and creates one Cloudinary bean. Its secure setting requests HTTPS delivery URLs.

Cloud upload workflow:

User selects image in galleryPage2.html
        -> multipart/form-data POST /gallery2
        -> GalleryController receives MultipartFile
        -> image.getBytes()
        -> cloudinary.uploader().upload(bytes, empty options)
        -> Cloudinary response map
        -> secure_url extracted
        -> ImageTable2.imageUrl assigned and saved by Image2Repository
        -> controller reloads cloudImages from database
        -> galleryPage2.html renders image.getImageUrl() in img elements

The project also implements a local-gallery workflow in GalleryController: MultipartFile bytes are Base64 encoded, stored in ImageTable, associated to the current session user where found, placed in session.totalImages, and rendered by galleryPage.html as a data URL.

12. REST API DEVELOPMENT AND RESPONSEENTITY
-------------------------------------------

REST controller files: RController/RControllerClass.java and AuthRestController.java.

API endpoints:
* POST /api/auth/login — authenticates credentials and returns {"token": "..."}; returns 401 UNAUTHORIZED for invalid credentials.
* GET /api/hello — returns 200 OK and "Hello World".
* GET /api/users — returns 200 OK with List<UserTable>, or 204 NO CONTENT when the list is empty.
* GET /api/users/{id} — returns 200 OK with a user; a nonexistent id is translated to 404 NOT FOUND.
* POST /api/users — accepts a JSON UserTable and returns 201 CREATED with "Saved Successfully".
* PUT /api/users/{id} — accepts JSON user details, updates mutable fields, and returns 200 OK with the saved user.
* DELETE /api/users/{id} — removes an existing user and returns 204 NO CONTENT.

Request and response strategy
@RequestMapping("/api") supplies the common resource root. @GetMapping, @PostMapping, @PutMapping, and @DeleteMapping express HTTP intent. @RequestBody accepts JSON entity payloads; @PathVariable reads resource identifiers; @RequestParam accepts login parameters. ResponseEntity gives each endpoint explicit response bodies and status codes: 200, 201, 204, 400, 401, 404, and 500 are represented by the success and exception flows.

13. EXCEPTION HANDLING
----------------------

Files: Exception/GlobalExceptionHandler.java and UserNotFoundException.java.

GlobalExceptionHandler uses @ControllerAdvice and @ExceptionHandler methods to create consistent HTTP error outcomes:
* UserNotFoundException -> 404 NOT FOUND with the exception message.
* ConstraintViolationException -> 400 BAD REQUEST with a joined "Validation Error" message.
* Any other Exception -> 500 INTERNAL SERVER ERROR with an error message.

This centralizes REST error translation instead of duplicating response construction inside every endpoint. UserNotFoundException represents the explicit absent-user case used by user GET, update, and delete actions.

18. SECURITY IMPLEMENTATION
---------------------------

Credential and secret management
application.properties uses ${...} placeholders for all database passwords, SMTP credentials, JWT secret, and Cloudinary credentials. render.yaml declares these values as sync: false, so deployment configuration accepts values without storing them in repository source.

Authentication and access control
BCrypt protects stored account passwords. The browser login flow verifies the BCrypt hash before creating a session. The API login flow issues a short-lived-by-configuration, HS256-signed JWT; protected /api/** endpoints require authentication and the JWT filter establishes that authentication from a valid Bearer token.

Validation and error boundaries
User entity constraints express required username, password, and valid email data. Registration and login controllers reject empty required form fields before processing. Controller advice uses distinct HTTP errors for missing users, validation violations, and unexpected failures. Image and mail integrations handle I/O/delivery exceptions at their integration calls.

Transport-aware image delivery
Cloudinary is configured with secure=true, and GalleryController persists Cloudinary's secure_url for HTTPS image rendering.

19. COMPLETE USER AND TECHNICAL FLOW
------------------------------------

Browser registration and login flow

Visitor opens /
  -> firstPage.html links to /signup or /login
  -> signup.html submits username, email, password
  -> SignupController checks populated fields and duplicate username
  -> UserServiceImpl BCrypt-hashes the password
  -> UserRepository/Hibernate saves UserTable
  -> EmailService sends registration email through SMTP
  -> redirect to /login with signup confirmation
  -> login.html submits username and password
  -> UserServiceImpl retrieves user and BCrypt verifies password
  -> MappingClass creates HTTP session with username
  -> redirect to /home; Thymeleaf renders the user list

Gallery flow

Authenticated browser user opens /gallery
  -> controller checks session username
  -> uploads multipart image
  -> bytes are Base64 encoded and stored in ImageTable
  -> session.totalImages is refreshed
  -> galleryPage.html renders Base64 image data

Cloud gallery flow

User opens /gallery2
  -> gallery page loads ImageTable2 URL records
  -> upload form posts a multipart image
  -> Cloudinary accepts image bytes
  -> secure_url is saved as ImageTable2.imageUrl
  -> gallery page renders the saved HTTPS URL

API flow

API client posts credentials to /api/auth/login
  -> BCrypt credential verification
  -> JWT response
  -> client passes Authorization: Bearer token to /api/users
  -> JwtAuthenticationFilter validates and populates SecurityContext
  -> SecurityFilterChain allows authenticated /api request
  -> REST controller/service/repository performs operation
  -> ResponseEntity returns status and payload; ControllerAdvice translates raised errors

MySpringWeb is a complete Spring Boot web application that demonstrates modern Java enterprise development from frontend interaction to deployment configuration. It provides account registration and secure password handling, browser-session access, authenticated REST CRUD operations, JWT bearer authentication, database persistence with entity relationships, Thymeleaf-rendered pages, SMTP registration emails, local and Cloudinary-backed image galleries, centralized API errors, and container-ready deployment assets.

The codebase is organized into clear layers that make its request flow understandable and maintainable: controllers handle web/API input, services apply application rules, repositories persist entity state, configuration supplies security and integrations, and templates render the browser interface. External credentials remain runtime configuration rather than source values, while the Docker and Render definitions provide a direct deployment path. This makes the project suitable as a demonstrable full-stack Spring Boot submission and as a foundation for future development.
